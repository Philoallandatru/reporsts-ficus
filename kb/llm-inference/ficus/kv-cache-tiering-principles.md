# KV Cache 分层的五条原理

**显存放不下想保留的历史时，分层只是三个选项之一；能不能靠分层拿到收益，要看搬运的收支、粒度的取舍、谁来决定模型可见历史，以及恢复条件是否同时成立。**

## 背景 / 为什么

做 KV cache 分层方案时，最容易跳过的是原理层：直接进入「用什么结构存」「放哪一级」的实现细节。结果是方案能跑通，但说不清收益从哪来、风险在哪。

这五条原理的作用是：**在动手之前先判断这件事值不值得做**。它们不依赖任何具体框架，四家开源项目（Strata / KVMem / LMCache / Mooncake）的差异，都能还原成在这五条上做了不同取舍。

## 核心内容

### 原理一：显存是固定的，KV 是线性增长的

一段上下文的 KV 字节数：

```text
KV 字节 = 2 × 层数 × token 数 × kv_heads × head_dim × 每元素字节数
          ↑ K 和 V 两份

```

它随保留的 token 数**线性增长**，不随模型变小而变小。再叠加两件事：并发会话继续累加（N 个会话就是 N 份），显存还要装模型权重、计算缓冲和 CUDA graph。

于是出现硬边界：**「想保留多少」和「显存能给多少」是两条不同曲线**——一条直线上升，一条水平线。交点之后只剩三条路：丢历史、每次重算、把历史放到更慢的介质。第三条才是分层。

```text
      想保留的 KV（随上下文线性增长）
               |
         8K ---+
        32K ---+-----
       128K ---+-----+-------
         1M ---+-----+-------+---------
               |
               v
        +-------------------------------+
        | 一张卡的显存（固定水平线）    |
        | [权重]  [计算缓冲]  [KV 余量] |
        +-------------------------------+
               |
          放不下时只有三条路
               |
+--------+      +----------+   +--------------+
| 丢历史 |      | 每次重算 |   | 下沉 RAM/SSD |
| (有损) |      | (慢)     |   | (分层)       |
+--------+      +----------+   +--------------+
```

### 原理二：搬不搬，只取决于一个不等式

缓存命中本身不是收益。真正的判据：

```text
T_查找 + T_恢复 + T_剩余后缀的 prefill  <  T_从头 prefill 整段

```

**只要左边大于右边，命中反而更慢**——重算永远是一个合法替代方案，而且不需要任何缓存设施。

两个推论常被忽略：

- **收益同时取决于命中长度和恢复成本**。命中更长通常少算更多 token，但也要搬更多状态，净收益受模型、带宽和排队影响，不能只由命中率推断。
- **prefill 期间的搬运和 decode 期间的缺页代价完全不同**。prefill 是批量计算，搬运可以重叠在计算后面；decode 每步只算一个 token，一旦缺页，本步的注意力计算就得等。

```text
      恢复前缀的耗时
          │
   重算 ──┼─────────────┐  ← 对角线：两者相等
          │        ╱    │
          │      ╱      │
          │    ╱  命中划算│
          │  ╱           │
          └──────────────┼── 恢复前缀的耗时
                         │
        带宽下降 / 排队变长 → 命中点右移

```

### 原理三：整存与切块，是两种不同的赌注

同样是「把历史放到别处」，粒度决定你能拿到哪种收益：

| | 整会话 / 整序列存 | 块级存 |
|---|---|---|
| 一次存什么 | 一整条序列的状态（含所有相互依赖的部分） | 固定大小的 KV 块 |
| 天然优势 | 依赖关系一起走——recurrent、位置、indexer 状态不必单独建模 | 公共前缀可共享；可按需只调入一部分 |
| 天然代价 | 若只有整份快照，恢复只能回到已有检查点；不同会话会重复存各自的公共前缀 | 索引、调度、小笔 I/O 成本上来；块边界必须和引擎对齐 |

**没有免费的那一边。** 块越细共享越灵活，但越容易被小随机 I/O 拖垮。

```text
+-------------------------+    +--------------------+
| 整存：各存各的          |    | 切块：前缀可共享   |
| 快照 1 = 全量 A B C D   |    | 块 ABC（只存一份） |
| 快照 2 = 全量 A B C E   |    |   ├── 块 D         |
| ↑ 公共前缀 ABC 存了两份 |    |   └── 块 E         |
+-------------------------+    +--------------------+
```

### 原理四：搬回去 ≠ 让模型看见

这是四家最容易混淆、也最影响质量的一条：

- **完整搬回**（恢复模型这一步本来需要的全部历史）→ 计算语义不变，只省了 prefill。
- **为预算再筛一遍**（显存装不下，只放回一部分）→ 模型能利用的证据变了，答案可能变。

区别不在「有没有搬运」，而在**谁决定模型这一步能读到哪些页**：

```text
Strata（模型自己选）          KVMem（额外策略选）      
-------------------------     ------------------------ 
QSA indexer 按 query 打分     完整历史留在 host        
        |                             |                
模型定下 top-k 页             额外评分：mean-K / 图传播
        |                             |                
驻留器把这些页全部搬到显存    按显存预算取 top-k 工作集
        |                             |                
attention 看模型选中的页      attention 看这个工作集   
= 模型原本的稀疏注意力        = 原模型 ∩ 策略选择      

结论：前者不引入新的可见性损失，后者可能漏掉模型本会读到的页
```

**判据**：搬运层若能保证「模型原生需要的页全部到齐」，就不改变答案；一旦为预算再裁一次，就必须单独评估质量。

### 原理五：查到候选、读到字节、能继续推理，是三个独立条件

初学者最容易把「前缀相同」当成「可以直接用」。实际要同时满足：

```text
  ① 身份匹配          ② 字节可读             ③ 执行状态可续
  token/图片/模式一致 → KV payload 存在且布局兼容 → 位置、checkpoint、
                                                        recurrent 对得上
        │                     │                          │
        └─────────────────────┴──────────────────────────┘
                              ▼
                    才真的能跳过这段 prefill

  常见误解：以为查到候选就结束了

```

第 ③ 条经常卡住：

- **KV 依赖它之前的全部上下文**——同一段 token 放在不同前缀后面，数值不同；
- **混合模型还需要同一边界的递归状态**（Qwen 的 GDN），attention KV 对上了但 recurrent 没对上，仍然不能续算；
- **位置编码参与身份**——M-RoPE 下多个 token 可能共享同一个 `pos`，按位置删会误伤邻居。

这解释了为什么四家都在「键」之外额外做身份校验：Strata 用 config + 模型采样指纹，LMCache 把 model/rank/dtype 编进 key，KVMem 用 `BackendIdentity`，Mooncake 把这件事整个交给调用方。

```text
              │

[原理四] 谁决定模型本步能读哪些页？（完整搬回 vs 为预算再筛）
              │
              ▼
[原理五] 身份 + 字节 + 执行状态 三者同时成立才跳过 prefill

四家在这条链上的取舍
  Strata   细块 + 模型原生选页（不额外裁剪）
  KVMem    块级 + 主动接受额外裁剪，换更大工作区
  LMCache  块级 + 身份校验压进 key，坚持精确复用
  Mooncake 不选——字节容器，把三条全部推给调用方

```

## 关键要点

- 分层不是目的，是「丢历史 / 重算 / 下沉」三条路里的一条；先确认另外两条不可接受。
- 命中不等于收益，收益来自「省下的 prefill 覆盖搬运与恢复成本」这一个不等式。
- 交换粒度决定了公共前缀能否共享，也决定了索引和调度的开销，没有两边都占的方案。
- 搬运层若替模型做了额外的可见性裁剪，就必须独立评估答案质量，不能只看延迟。
- 混合模型（attention + recurrent）恢复时，recurrent 状态和 KV 的边界必须对齐，否则无法续算。
- 判据要落到具体系统的实际延迟上；本系列是纯静态阅读，没有跑过性能基准。
