# 控制器（Controller）

控制器是主机进入 NVM 子系统的“服务窗口”。它从主机提交的队列中取命令，协调数据访问，再把结果放入完成队列；主机不会直接操作底层闪存。 [PDF p. 29](../_source/pages/page-029.md)

## 先看一次读操作

```text
主机应用 --> 驱动 --> 提交队列 --> 控制器 --> 命名空间/存储资源
                                  |
                                  +--> 完成队列 --> 驱动 --> 应用
```

这是解释性流程图。控制器负责命令处理和队列协作；命名空间才是主机读写的逻辑存储对象。 [PDF pp. 29, 58-60](../_source/pages/page-029.md)

## 一个常见案例

数据库发出一次写入。NVMe 驱动将命令放入提交队列并通知控制器；控制器执行后写入完成队列。驱动通过命令 ID 找到原请求，再通知数据库“写入已完成”。

因此，“控制器很快”并不仅是介质快：它还要能正确管理并行队列、命令状态和完成通知。 [PDF p. 29](../_source/pages/page-029.md)

## 控制器的三种角色

| 类型 | 它做什么 | 能否直接处理用户 I/O |
|---|---|---|
| I/O 控制器 | 访问命名空间，也可以承担管理工作 | 可以 |
| 发现控制器 | 帮助主机在 Fabrics 环境中发现服务 | 不可以 |
| 管理控制器 | 管理命名空间、虚拟化、健康或子系统操作 | 不可以 |

三种控制器都需要一对管理队列。控制器通过 Identify Controller 数据结构的 `CNTRLTYPE` 报告类型。 [PDF pp. 59-62](../_source/pages/page-059.md)

## 静态与动态：关掉连接后会怎样

```text
静态控制器：固定 ID，保存的配置可在控制器级重置后保留
动态控制器：按需分配，新的会话从没有历史状态开始

PCIe（基于内存） --> 静态
Fabrics（基于消息） --> 可为静态或动态
发现控制器 --> 动态
```

这张图是规范规则的学习用归纳。动态并不表示性能更差，而是表示连接生命周期与状态保留方式不同。 [PDF p. 58](../_source/pages/page-058.md)

## 初学者的配置案例

一台 Fabrics 存储可以向管理员提供管理控制器，向业务服务器提供 I/O 控制器，还提供发现控制器帮助新主机找到服务。它们在同一子系统内，但职责不同：发现和管理不能代替用户数据 I/O。 [PDF pp. 59-62](../_source/pages/page-059.md)

## 不要把这些维度混为一谈

| 维度 | 可选值 | 回答的问题 |
|---|---|---|
| 传输模型 | 基于内存 / 基于消息 | 命令和数据怎样传递？ |
| 分配模型 | 静态 / 动态 | 控制器何时创建、状态是否保留？ |
| 功能角色 | I/O / 发现 / 管理 | 它能提供什么服务？ |
| 资源角色 | 主控制器 / 从属控制器 | 虚拟化资源怎样管理？ |

例如，“使用 PCIe 的静态 I/O 控制器”同时占据了前三个维度，并不是一个新的单独类型。 [PDF pp. 28-35, 58](../_source/pages/page-028.md)

## 进阶细节

管理控制器可以管理子系统级对象，甚至可以存在于没有命名空间或非易失性介质的子系统中。主从控制器则是虚拟化资源管理维度：从属控制器依赖主控制器管理虚拟队列和虚拟中断资源。 [PDF pp. 34-35, 61-62](../_source/pages/page-034.md)
