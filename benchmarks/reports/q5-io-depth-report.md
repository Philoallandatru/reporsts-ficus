# Q5 专家读队列：深度 1、2、4、8 的隔离实验

2026-11-11。续 [Q5 三方对照](../runs/q5-strata-compare-20261111/REPORT.zh-CN.md)。这次只筛选 P6 读取端的在途槽容量。Q5 仍使用原来的 GPU MoE、完整路由、缓存策略和 Windows 文件读取路径。

**深度 8 通过短测筛选，建议作为下一轮长测候选；生产默认仍保留 2。** 固定权重、路由、缓存和 staging 后，两轮 decode 分别比深度 2 快 **10.4% / 16.5%**，中位吞吐 **2.29 → 2.60 tok/s（+13.5%）**。两轮 token p99 分别是 **1.320 → 1.314 s**、**1.259 → 1.070 s**。深度 4 的中位收益约 **8.5%**，第二轮 p99 增加 **15.6%**，未通过预设门槛。

| 在途槽 | 两轮 decode tok/s | 中位 tok/s | 中位 TTFT | 两轮 token p99 | Q5 物理读 MiB/token | 磁盘 `QD/I` p50/p95 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 2.01 / 0.67（补采） | 1.34 | 35.64 s | 2.074 / 11.374 s | 461.15 | 0 / 0 |
| 2 | 2.28 / 2.30 | 2.29 | 29.23 s | 1.320 / 1.259 s | 461.15 | 0 / 0 |
| 4 | 2.44 / 2.53 | 2.48 | 23.51 s | 1.128 / 1.455 s | 461.15 | 0 / 0 |
| 8 | 2.51 / 2.69 | 2.60 | 24.21 s | 1.314 / 1.070 s | 461.15 | 0 / 1 |

TTFT 从提交请求到首 token，包含 prefill；decode 使用首末 token 间的 127 步。冻结 DLL 深度 2 单跑 **2.305 tok/s**，与候选深度 2 接近。四档进程工作集峰值均约 **21.52 GiB**、private commit 约 **29.57 GiB**。专家预算仍是约 4 GiB 显存、16 GiB RAM；工作集上限仍是 24 GiB。完整九次运行都无 ETW 丢失，全部 logits 与冻结版逐位一致，decode 专家物理区间多重集合指纹也全部一致。

原第二轮深度 1 完成了同轨迹输出，但出现连续慢段，decode 只有 **0.72 tok/s**，最长间隔 **31.9 s**。ETW 顺序文件达到 1,536 MiB 上限，停止时 logger 已不存在，未留下完整 ETW 或写出的 logits。保留原日志与计时；先按原顺序完成深度 4/2，最后在 3,072 MiB 文件上限下补采深度 1。提高上限不改变事件或采样频率。两轮筛选不能判定深度 1 的低概率慢段发生率，也不能证明深度 8 治好了慢读。

补采也重现了慢段。补采整轮 decode 专家盘读单笔 p95 **18.64 ms**，其余正常样本约 **1.1–1.3 ms**。最慢的输出步等了 **13.42 s**，其中 **12.25 s** 与 578 笔专家磁盘读取重合（按时段并集计时），该步最长单笔约 **34.44 ms**。补采整轮没有一笔专家读超过 100 ms。该轮是大量串行读取变慢后累积成 token 慢段，不能据此区分磁盘、驱动、文件系统或共享主机造成的速率变化；原 31.9 秒慢步缺少完整 ETW，不能套用补采的单笔解释。

**收益来自同样的工作更早做完。** 深度 2、4、8 每次请求均为 86,217 笔应用专家读、87.63 GiB 逻辑字节和 87.96 GiB 对齐字节。应用统计包含 prefill；只看 decode，ETW 看到相同的物理专家区间及次数，Q5 每步约 461.15 MiB。深度 2→8 时，从首末 token 区间算出的物理读取吞吐约 **1.03 → 1.17 GiB/s**。整个请求里，等待已提交专家读的两轮中位总时长约 **36.0 → 28.2 s**，上传等待约 **20.0 → 17.9 s**。这两个计时是应用等待，不能直接当成磁盘服务时间或 CUDA 拷贝时间。

深度 8 的槽仍在 FIFO 中复用：文件读结束后还要填 RAM、提交上传和等 GPU 事件；RAM 命中也占用槽。应用在途槽确实用到了 8，磁盘侧 `QD/I` 却仍然很浅。所以候选能减少部分等待，但没有复现上次 Strata 正常轮观察到的 `QD/I` p50/p95 约 5/18，也没有减少每个 token 的读盘量。

## 同文件映射的独立对照

脱离模型和 GPU，固定 Q5 第四分片的 1,536 笔读、8 个槽、32 MiB staging，`ReadFile` 保持 `NO_BUFFERING | OVERLAPPED | RANDOM_ACCESS`。四轮顺序为**不映射、映射、映射、不映射**；仅切换被动只读映射，始终持有同样的普通文件句柄，不访问映射里的数据。四轮的物理读取均为 **1,956 MiB / 1,543 笔**，物理区间指纹相同，ETW 无丢失。

| 顺序 | 保留映射 | GiB/s | `ReadFile` 提交耗时 p95 | 磁盘 `QD/I` p50/p95 |
|---:|:---:|---:|---:|---:|
| 1 | 否 | 1.41 | 43.1 µs | 0 / 0 |
| 2 | 是 | 1.45 | 53.0 µs | 0 / 0 |
| 3 | 是 | 1.43 | 40.4 µs | 0 / 0 |
| 4 | 否 | 1.52 | 44.9 µs | 0 / 1 |

释放映射两组成对吞吐 **−3.0% / +6.1%**，没有一致收益，也没有把设备侧队列变深到 Strata 正常轮的量级。这个隔离实验只覆盖被动映射，不覆盖模型主动缺页或内存压力下的竞争，也没有重现模型的慢段。现有证据不足以优先重做 loader 映射。原始结果见 [映射数据](../runs/q5-io-depth-20261111/map-probe-results.json)，探针与采集器见 [map_probe.cpp](../runs/q5-io-depth-20261111/map_probe.cpp)、[run_map_probe.py](../runs/q5-io-depth-20261111/run_map_probe.py)。

## 下一步

1. 先保留现有缓存和文件路径，只对深度 2/8 做 8K 提示、较长输出的交替对照；先筛 1,024 输出，再决定是否跑满旧 P5/P6 的 7,680 输出。仍核对 p99、最慢步、每步物理读、工作集、commit 和逐位 logits。短测是继续验证的依据，不能改默认。
2. 若要提高实际磁盘并行度，先给读提交、读完成、RAM 填充和上传事件分别计时。再验证能否让新读与较早的 GPU 上传独立推进；中转缓冲和缓存租约仍须等最后一个消费者用完。只有读调度已能维持实际在途量，才有条件单独测合并区间能否摊薄提交而不放大读量。

## 改了什么，没改什么

P6 的在途槽同时持有文件读取、中转数据和上传相关的状态。原本上限为 2；候选把上限放到 8。每次仍按原顺序：提交文件读 → 等读完成 → 如需则填 RAM 缓存 → 上传并等事件 → 释放租约。候选没有引入合并读取、异步上传完成乱序、双层缓存互补或 CUDA 内核变化。大于 2 的深度不是生产默认值；本轮未修改生产工作树和原始 P6。

总 staging 始终 32 MiB，深度 8 时每槽接近 4 MiB，仍能容纳本次 Q5 专家的最大角色与对齐空隙。控制结构增加约 1 KiB，单独记账。PLE 维持深度 2 和 64 MiB RAM 预算。候选在独立目录只重编 `llama-expert-store.cpp` 并重链接，其余目标文件复用冻结构建；[构建身份](../runs/q5-io-depth-20261111/build-identity.json)与[实验 patch](../runs/q5-io-depth-20261111/depth-only.patch)记录了输入及产物。对照臂使用同一个探针，约 121 MiB logits 先存在内存，ETW 停止后写盘。

## 安全与数值检查

本轮在隔离副本扩展了原 expert-store 测试。在深度 8 真正占满槽时分别注入读中取消和已提交上传之后的失败。核对 8 个读取槽全部排空，或 7 个读取槽与 1 个上传槽排空，部分缓存条目无效，租约归零；随后的完整读取逐字节一致，且重复访问可以命中。原本的 GPU 事件、H2D 失败排空、混合大小和 PLE 检查也通过。见 [单测日志](../runs/q5-io-depth-20261111/unit-test.log) 与 [新增测试](../runs/q5-io-depth-20261111/depth_test.inc)。

全部正式运行使用和三方对照相同的 128 个 prompt token 和 128 个强制输出 token。冻结版深度 2 的全部 31,784,960 个 float32 logits 与 P6 原归档逐位一致；候选按同一位模式核对，不能仅凭输出 token 相同验收。测量条件、筛选阈值及轮换顺序见[协议](../runs/q5-io-depth-20261111/PROTOCOL.zh-CN.md)。
