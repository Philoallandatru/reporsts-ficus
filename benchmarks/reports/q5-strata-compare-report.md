# Strata 相对 llama.cpp 提升了什么：Q5 同工作量对照与改造路线

日期：2026-11-11。范围：本机 Windows、单张 RTX 5080、Qwen3.8-Flash-Next UD-Q5_K_XL（147.42 GiB），以及冻结的 llama.cpp b12211、P6 和 Strata 0.1.58。这里比较的是本机已验证的三条推理路径，不代表其他模型、操作系统或版本。

**结论：24 GiB 工作集上限下，P6 的 Q5 decode 中位数是 2.36 tok/s，原生参考是 1.75 tok/s，P6 +35.1%。Strata 是 2.21 tok/s，三个循环中没有稳定的 decode 优势；它的 READY 后首 token 更快，11.28 对 28.97 秒。** 历史 Strata 的数倍吞吐差距没有在对齐预算、关闭 MTP 和尾跳后复现。

## 同条件数据

各臂 **3 个有效样本**，轮换顺序。相同六个 Q5 分片、同一 128-token 提示和同一 128-token 强制输出；统一 32K context、单序列、16 个逻辑核。各次逐 token IDs 均匹配；Strata 每次 0 草稿、0 prompt 复用，decode 的 **61,440 路由条目**等于 `128 × 48 层 × top-10`。Strata 的 `--spec 2` 只建立 verifier，日志确认 `mtp_max=0`、`lookup=0`，没有 MTP 文件或专家尾跳。共同计时从首 token 到末 token，分母 127；TTFT 从提交输入到首 token。

三者 Windows 进程硬工作集上限都是 **24 GiB**，专家 GPU 缓存共同上限 **4 GiB**：两条 llama.cpp 路径实配 **4,091.94 MiB**，Strata **4,066 MiB（1,067 槽）**。P6/Strata 专家 RAM 分别实际约 **16,383 / 16,382 MiB**；原生没有独立 RAM 专家池，用受工作集上限约束的 `mmap`，仍可命中进程外的系统文件缓存。这个对照匹配了可施加的预算，不把相同工作集上限说成等同的全系统 RAM 上限。两种引擎实际 KV 表示、prefill 和计算调度仍可不同。

把每次的「首样本到 READY」与「提交后到首 token」相加、排除测量器的固定等待，P6 和 Strata 的中位数分别为 **32.00、33.58 秒**；这两个阶段之和是估计，不是单独测过的冷启动服务延迟。三组最低系统 commit 余量分别为原生 **25.04 GiB**、P6 **8.56 GiB**、Strata **5.95 GiB**，都没有触发 4 GiB 保护线。

² xperf `QD/I` 是该盘发起请求时观察到的在途数，属于设备侧观测，不能当成应用配置的队列上限。读取量按同一 PhysicalDrive2 上的 Q5 分片 DiskIO 完成事件逐条求和；全部请求有完整 ETW 覆盖，零丢事件/缓冲，decode 的 Q5 读均归属于对应进程。不是 NAND 内部流量，也不混入 P6 的逻辑字节。旧 P6 的 385 MiB/decode 排除了前 32 步且是逻辑计数，本轮包含整个首末 token 窗口。

**为什么有了不同于旧基线的结论？** P6 在 24 GiB 限制下有 3/3 轮比原生参考快，工作集中位数约少 2.6 GiB，但 private commit 多约 16.2 GiB。原生读的物理字节最少，说明它仍有效使用文件页缓存；它的单笔读典型只有 64 KiB，而 P6 约 1.1 MiB。大量小请求、缺页与 CPU/GPU 交接的总成本可以盖过少读字节的收益。这是本轮观察到的路径差异，尚未逐项消融。旧 P5 在 48 GiB 上限下原生更快，因此结论随资源条件而变。

**Strata 的优势落在哪里？** 本轮 Strata 三次 TTFT 都在约 11–12 秒，明显早于 P6；代价是 READY 前的专家预装。本轮 Strata 每步物理读取多于 P6，两个正常轮次的读吞吐分别为 1.43、1.23 GiB/s，且读请求更常重叠，单笔大小却与 P6 接近。它的批量读取和 CPU/GPU 分工是解释候选，不能把差异完全分给某个内核、一次合并或单独的缓存策略。

按 Strata `DONE` 的全路由分母核对，三个循环中约 **56–59%** 的专家条目交给 CPU、约 **8–10%** 由 GPU 经 PCIe 处理，其余约 **33%** 在 GPU 缓存命中。这证明混合计算在本轮确实运行；条目比例不能换算成时间比例或实测 PCIe 字节。P6 的小批桶记录 **0 个 CPU miss**，上传计数的作用域和 Strata 路由条目不同。

**慢段是真的，也会出现在 Strata。** 其第 2 轮与第 1 轮每步物理读分别约 574 与 577 MiB，读取吞吐却从 1.43 降到 0.43 GiB/s；专家读完成时间 p95 约 9.7 → 129 ms，最长 token 间隔 12.84 秒。该次 Strata 已关闭专家映射，仍完整运行并恢复。它说明慢段不是多读了大量字节，也不以保留映射为必要条件；仍不能锁定 SSD 硬件、驱动或调度根因。

**两份非正式样本均保留。** 未修改的 b12211 默认预取在加载期把系统 commit 余量压至 3.29 GiB，触发 4 GiB 保护线；这不是观测到 OOM，也不是一个有效吞吐样本。正式原生参考只关掉预取。Strata 试配 1,070 个参数槽实际得到 4.41 GiB，超出共同 GPU 预算，调整后才纳入对照。


## 三条路径分别做了什么

**原生 mmap。** GGUF 文件映射进虚拟地址空间，触碰尚未驻留的页时由 Windows 文件映射和页缓存提供。模型文件超过 RAM 与显存总量，仍可能完成推理。b12211 已有 MoE GPU 缓存：缓存命中在 GPU 算；未命中可上传所需专家，原生也有可选 CPU miss。P6 并未发明 GPU 专家计算。对照采用 `llama.cpp/docs/moe-cache.md` (上游 MoE cache)，原生参考仅把加载预取关掉，避免把原生默认加载的资源保护中止混进速度比较。

**P6。** loader 登记分片、量化张量与专家偏移；GPU miss 先查程序自己的 RAM 专家缓存，再通过 Windows 无缓冲读从 GGUF 取所需权重。固定 staging、两个在途槽和后端完成事件负责读取、上传、回收。显存缓存仍由原有策略控制。P6 把 RAM 槽按精确字节数分组，减少小张量占大槽的浪费，但没有协调两级缓存的保留和淘汰。PLE 查找表另走紧凑行缓存。入口见 `llama.cpp/docs/development/file-expert-store.md` (开发文档)和 `llama-expert-store.cpp::transfer`；一般 prefill 上传可使用已有 RAM 命中，miss 已经绕过准入。

**Strata。** 从权重驻留到算子调度共同考虑，主要机制如下。完整的分支条件、实际运行记录和源码行号在[源码附录](../runs/q5-strata-compare-20261111/SOURCE-REVIEW.zh-CN.md)。

| 环节 | Strata 如何实现 | 相对 P6 的意义 |
|---|---|---|
| 两级专家驻留 | 根据 profile 先填显存。`FileExpertSource::pin_cache_complement` 再按热度选显存里没有的专家放入有预算的锁页 RAM。适应性换入可把被换出的显存专家交回 RAM，交换有同步和拷贝成本。Prefill 借用区存在有意重复的例外。 | 相同字节预算能覆盖更多不同的专家，并减少冷启动时靠扫描填缓存的过程。P6 的历史 Q5 短测末尾有约 3.43 GiB 重复权重；是否能把这些字节换成更多命中，取决于轨迹和换出代价。 |
| 冷权重的文件 I/O | 同分片内按偏移组织，对齐、排序并合并适合的区间，批量提交后再等待。切到无缓冲路径后释放原专家映射；本轮应从日志核对。 | P6 的单请求是专家角色范围，深度只有两个在途槽。批量读取可以提高队列并行度、摊薄提交成本；合并间隙过大也可能增加物理读取。Strata 释放映射而 P6 保留映射是可验证的 Windows 路径差异，尚不是慢读的因果结论。 |
| Decode 的 CPU/GPU 分工 | GPU 算显存命中；部分主机专家可由 GPU 经 PCIe 处理，其余由 CPU 池直接算，最后汇合。device hit path 和较长 CUDA Graph 减少逐层回到主机的等待。 | P6 当前保持完整 top-10 全部专家由 GPU 计算，RAM hit 仍须上传。CPU 参与能省掉一部分权重上传，但增加对 CPU 计算、RAM 带宽和结果汇合的要求。旧 IQ2 的 Nsight 观察证明逐层同步存在，不能用它量化本次 Q5 的份额。 |
| Prefill 和 PLE | 大提示有按层的 Stager、host/GPU ring 与融合内核，必要时借显存专家槽给 prompt 工作缓冲；PLE 另外按行读取。 | P4 解决了文件模式的大批量入口、行缓存和工作区预算，尚没有同样的独立 prefill 流水。首 token 时间要单看，不能拿 decode 或 IQ2 长提示的倍率代替。 |
| MTP 与路由尾跳 | MTP 草稿让主模型可在一次验证中推进多 token；低排名且未命中的专家尾跳可以减少计算/读取，但会改变执行语义和输出。 | 历史 Strata 的 8.5–10.1 tok/s 同时开启这两项、使用更大缓存和不同请求。本轮关闭，两份数据不能相减来归因。 |

## P0–P6 交付的实际收益

| 阶段 | 可核验的价值 | 不能由此得出的结论 |
|---|---|---|
| P0–P2 | 固定可重放基线；用真实文件字节对比验证受控读取；接入已有 GPU 专家槽，控制分片读取与 staging，错误不继续执行受影响的图。 | 原生此前不能跑超容量 Q5，或本次首次把专家放到 GPU。 |
| P3 | 预算内的 RAM 专家缓存、异步双缓冲及上传完成前的租约保护；取消时排空。P5 同预算消融显示 depth 1→2 为 **2.00→2.26 tok/s（+12.9%）**。 | 双缓冲已经充分用尽 SSD 的带宽。 |
| P4 | 大批量文件专家路径、图工作区预检和微批次回退；PLE 不整表复制，量化行按需取。 | 已经实现 Strata 风格的 prefill ring 或等同的 CPU/GPU 混合计算。 |
| P5 | Q5 完成实际 8K prompt 与 7,680 输出、逐位校验和预算检查。在旧 48 GiB 工作集上限的同 GPU 缓存对照中，文件路径用约 **20.8 GiB** 工作集，原生参考达到 **48 GiB**；对应 **2.26 vs 4.44 tok/s**。长测文件路径工作集约 13.46 GiB。 | 原生在所有 RAM 约束下都更快，或文件路径的 private commit 也更低。旧短测的 private 为约 29.45 vs 13.32 GiB。 |
| P6 | 16 GiB 专家 RAM 内的槽位从 **9,868→12,875**；与 P5 的六组配对显示短测逻辑读取 **−16.96%**、decode **+9.26%**。租约/预算保持，全长 1,907,097,600 个 logits 与原生 GPU 参考逐位一致。 | 已达到预设 +10%，读盘长尾已解决，或 P6 和 Strata 逐位等价。旧长测慢读必须保留。 |

结论应写成一条资源曲线：RAM 约束较松时，原生 mmap 能用更多常驻文件页获得更高吞吐；RAM 约束较紧时，哪一条快要用本轮的同工作集实验判断。工作集、private commit 和系统缓存分别报告，不能合并成一句「省内存」。旧结果见 [P5](../runs/ooc-p5-20261110/RESULTS.zh-CN.md)与 [P6](../runs/ooc-p6-20261110/RESULTS.zh-CN.md)。

## 建议怎样改 llama.cpp

**先验证有界批量读取和慢段，再决定如何改缓存。** 这轮在可比预算下，Strata 每步读的物理字节并不更少，但正常轮次有更深的读队列和更高的读取吞吐。P6 的典型读大小已经和 Strata 接近，因此第一步应验证能否安全地让多笔读同时在途；不能假设把区间合并得更大就一定快。

1. **保持 P6 作为基线，分开测试 I/O 变量。** 用相同 GGUF 文件范围和相同 staging 总预算做短回放：先只改变同时在途的读数量（例如 1/2/4/8），再单独比较是否合并相邻区间。记录单笔提交到完成时间、队列深度、物理字节、MiB/s、端到端 p95/p99，保留慢段。作为另一个独立诊断，在隔离读实验中比较保持/释放同文件映射；正式引擎不能简单丢掉当前用作 tensor 地址与身份的映射。Strata 自己在已释放映射时也出现慢段，故不能把释放映射当成修复。候选 patch 放在 `llama-expert-store.cpp::transfer` 的读取端，保持原 GPU 槽位、事件租约和失败排空。用相同预算、固定轨迹和逐位 logits 复核，再判断是否值得合入。
2. **如果重点是交互响应，单独做 prefill。** 先按阶段量化 prefill 的普通专家上传、PLE 与 GPU 图准备，再试按层组织上传、复用已在 GPU 的专家、调整物理微批或安排 host/GPU 双环。P4 的一般上传已实现 miss 绕过，下一步是测量现有路径的搬运和批次成本。报告同时列 READY 前的启动时间，避免把 Strata 的启动预装成本隐藏在更短的 TTFT 背后。
3. **用 trace 验证互补驻留，然后再改策略。** P6 每步字节还可下降，且两级缓存存在可回收的重复空间；先用固定预算回放比较现有 LRU、profile 准入、显存/RAM 补集、显存换出交回 RAM。把换出回传字节和同步成本算进去，目标是减少真实 miss 与物理读，不是单纯降低重复字节。Strata 本次并没有比 P6 少读，不能把较高的理论独立容量直接当作对这条轨迹的收益。
4. **CPU/GPU 混合计算与 MTP 单列后续。** 只对已在 RAM 的一部分 GPU miss 试 CPU 计算，先核对量化格式、结果汇合、同 GPU 执行的逐位基准和跨设备容差。P5 的 CPU fallback 曾超出容差，当前不能把混合计算当作等价替换。GPU 内路由与更长 CUDA Graph 可以减少每层等待，但跨越 scheduler 和内核，适合作为独立工作。MTP 按实际接受率、主模型计算行数和质量单独对照；尾跳专家是近似策略，明确允许改变输出时才做独立质量试验。

短实验建议按同一轨迹和 4/16 GiB 缓存、24 GiB 工作集复核，继续输出物理 MiB/token、TTFT、吞吐、p99、资源余量和精确比对。验证一项，再用实际 8K 提示和长输出确认没有放大读盘、尾延迟或内存成本。提高预算的扫描可以说明机器能跑多快，应该单列成容量曲线。

## 理解改进原理所需知识

1. **MoE 与推理阶段。** 先学 top-k 路由、prefill/decode、KV 和专家工作集。练习：给一层四个 token 的路由列表，手算专家去重和 GPU/RAM/SSD 三种命中。明白「一条路由」、「一次专家请求」和「一个输出 token」是不同分母。
2. **GGUF 与 ggml。** 学分片偏移、量化块大小、`nb` 步长和 `MUL_MAT_ID` 的调度。练习：从一个 expert role 的 `offset + id * stride` 算出文件范围，再考虑对齐和同分片相邻范围。按 `llama.cpp/docs/development/file-expert-store.md` (文件路径说明)跟进 `llama-moe-cache.cpp` 的上传回调。
3. **操作系统文件页与异步 I/O。** 能解释 mmap 只占虚拟地址、文件页何时驻留和回收，区分进程工作集、private commit、系统缓存和设备读。掌握 `OVERLAPPED`、扇区对齐、取消后仍须等完成、队列深度与读放大。练习：从本轮 `diskio.txt` 计算分片字节和请求次数，与应用逻辑读字节对照。
4. **C++ 资源寿命和 CUDA 流。** 理解 RAII、缓存租约、锁页缓冲、异步 H2D/D2H 和 CUDA event；能解释为什么仅「提交了 copy」还不能回收或覆盖数据。练习：阅读 `test-expert-store.cpp::test_size_groups` 及取消/GPU 事件测试，画出失败时的回收顺序。
5. **缓存政策、实验和数值。** 学 LRU 与频率 profile、准入与逐出、互补驻留，以及把同一请求交替重放的实验方法。先用完整 top-k 做对照；跨 CPU/GPU 或新算子用相同轨迹做容差与质量验证。学 MTP 时区分每个输出 token、每个 verifier window 和主模型实际计算的行数。

无需从大模型开始。先用现有混合尺寸单测，预测哪些请求会读盘、何时会淘汰、为什么不能提前释放缓冲。再读本轮的逐请求记录，试着解释「读得更少却可能更慢」；能说清条件与证据边界后，再尝试改上游的一处可独立验证的路径。
